# SPEC — Production-grade качество юридических документов KORGAN

Статус: активная спецификация работы в ветке `claude/korgan-legal-document-quality-v1vgeo`
База: `recovery/miniapp-api-1600-sg` · Railway-сервис: `korgan-miniapp-api-recovery-1600`

---

## 1. Objective

KORGAN должен составлять юридические документы как практикующий юрист Республики
Казахстан. Production-grade требуется для четырёх типов:

| ключ | документ | сторона |
|---|---|---|
| `claim` | Исковое заявление | истец |
| `pretrial` | Досудебная претензия | кредитор/заявитель |
| `pretrial_response` | Ответ на досудебную претензию | получатель претензии |
| `response` | Отзыв / возражения на иск | ответчик |

Целевые пользователи — клиенты MiniApp, которые подают документ в суд РК или
направляют контрагенту. Документ читает судья или юрист противной стороны, а не
пользователь чат-бота.

Не входит в объём: `contract` (договор) — существующий путь сохраняется без
регрессий, но профессиональный редизайн для него не выполняется.

## 2. Проблема, которую закрывает работа

Аудит production-пути (см. §9) выявил:

1. Госпошлина не рассчитывается, когда цена иска записана в стандартной
   юридической форме «2 400 000 (два миллиона четыреста тысяч) тенге» → иск
   никогда не достигает `filing_ready`.
2. Потолок госпошлины для юридического лица занижен вдвое (10 000 МРП вместо
   20 000 МРП по ст. 665 НК РК); ставки захардкожены мимо `korgan/data/rates.json`.
3. Необработанное `decimal.InvalidOperation` на длинной сумме → 500 из API.
4. Полный `pytest` красный (29 fail / 914 pass): тесты проверяют функции,
   которые в production подменены монки-патчем, поэтому баги 1–3 не ловились.
5. Претензия и ответ на претензию не имеют численного quality gate.
6. Претензия не имеет отдельного воспроизводимого расчёта требований.
7. Ответ на претензию и отзыв на иск не разделяют признанные и оспариваемые
   обстоятельства и не содержат аудита расчёта контрагента.

## 3. Capability map

Модули независимо тестируемы и строятся в порядке зависимостей.

```
M1  money-and-duty-truth          (нет зависимостей)
      единый источник истины для разбора сумм и госпошлины

M2  legal-fact-provenance         (нет зависимостей)
      классификация факта: FACT_FROM_USER / FACT_FROM_DOCUMENT /
      DERIVED_CALCULATION / VERIFIED_LAW / LEGAL_ANALYSIS / MISSING_FACT

M3  reproducible-calculation      (M1)
      структура расчёта денежного требования: основание, база, ставка,
      период, дни, формула, итог

M4  adversarial-document-schema   (M2, M3)
      признанные / оспариваемые обстоятельства + аудит расчёта контрагента
      для pretrial_response и response

M5  pretrial-professional-pipeline (M3)
      расчёт требований и численный quality gate для претензии

M6  document-quality-gates        (M1..M5)
      единый порог, единый набор аудитов для всех четырёх типов

M7  regression-and-evaluation     (M1..M6)
      production evaluation suite + negative tests
```

Порядок сборки: M1 → M2 → M3 → M5 → M4 → M6 → M7.

## 4. Модули

### M1 — money-and-duty-truth

**Что:** один модуль, который владеет разбором денежных сумм и расчётом
государственной пошлины. Все прочие реализации либо удаляются, либо делегируют
сюда.

**Acceptance criteria**

- `parse_amount_kzt` понимает все формы, встречающиеся в юридическом тексте РК:
  `2 400 000 тенге`, `2 400 000 (два миллиона четыреста тысяч) тенге`,
  `2400000 тг`, `12 000 000,49 тенге`, `2400000 KZT`, `теңге`, `₸`,
  неразрывный пробел ` `.
- Дробные тиыны округляются `ROUND_HALF_UP` до целого тенге.
- Сумма из 29+ значащих цифр не приводит к исключению — возвращается значение
  или `None`, но не `decimal.InvalidOperation`.
- `calc_gosposhlina_claim(amount, is_individual)` берёт ставку и потолок
  **только** из `korgan/data/rates.json`: физлицо 1 % / 10 000 МРП,
  юрлицо 3 % / 20 000 МРП.
- После установки всех production `install_*()` поведение функций совпадает с
  поведением до установки: **разрешено только сужение до Decimal-точности, не
  изменение результата**.
- Регрессионный тест выполняется в двух режимах: до и после
  `korgan.strict_bot` — оба должны быть зелёными.

### M2 — legal-fact-provenance

**Что:** явная внутренняя классификация происхождения каждого утверждения.

**Acceptance criteria**

- Перечисление `FactOrigin`: `FACT_FROM_USER`, `FACT_FROM_DOCUMENT`,
  `DERIVED_CALCULATION`, `VERIFIED_LAW`, `LEGAL_ANALYSIS`, `MISSING_FACT`.
- `MISSING_FACT` никогда не превращается в значение: функция, получившая
  `MISSING_FACT`, обязана вернуть пробел или пометку, но не подставить данные.
- Запрещённые к изобретению сущности имеют детектор: ФИО, БИН/ИИН, адрес,
  номер договора, дата, сумма, доказательство, факт оплаты, факт направления
  претензии — если значения нет в материалах, оно не появляется в документе.
- Классификация **внутренняя**: ни один ярлык не попадает в текст документа.

### M3 — reproducible-calculation

**Что:** структура расчёта денежного требования, пригодная к перепроверке.

**Acceptance criteria**

- Структура несёт: `principal`, `penalty_base`, `penalty_rate`, `start_date`,
  `end_date`, `days`, `formula`, `amount`.
- Рендер расчёта детерминирован: одинаковый вход → побайтово одинаковый выход.
- Если в материалах есть договорная неустойка (пункт договора + ставка),
  используется она. Замена договорной неустойки на ст. 353 ГК РК запрещена.
- Юридические услуги и судебные расходы — отдельные позиции расчёта и
  отдельные пункты просительной части.
- Недостающий элемент (нет ставки / нет периода / нет базы) → расчёт не
  выполняется, в `verification_notes` попадает указание, чего не хватает.
  Сумма не выдумывается.
- Итог расчёта согласован с ценой иска в той части, которая в неё входит.

### M4 — adversarial-document-schema

**Что:** профессиональная схема состязательных документов ответчика.

**Acceptance criteria (для `pretrial_response` и `response`)**

- Схема разделяет:
  - `admitted_circumstances` — обстоятельства, признаваемые доверителем;
  - `disputed_circumstances` — оспариваемые обстоятельства;
  - `calculation_review` — построчный разбор расчёта контрагента;
  - `settlement_offer` — предложение частичного исполнения/урегулирования
    (только при наличии оснований).
- Признание не создаётся автоматически: пустой `admitted_circumstances`
  допустим и не понижает оценку, если материалы не дают оснований признавать.
- Шаблонное «С требованиями не согласны» без обоснования блокируется.
- Возражение без указания обстоятельства, к которому оно относится,
  блокируется.
- Исковая давность упоминается только когда в материалах есть даты, из которых
  она вычислима.
- Процессуальные нарушения указываются только при фактическом основании.

### M5 — pretrial-professional-pipeline

**Acceptance criteria**

- `PretrialDraft` получает поле `calculation` (тот же формат, что в M3).
- Претензия содержит срок исполнения только из закона, договора или указания
  пользователя. Выдуманное число дней блокируется.
- Численный quality gate для `pretrial`: те же категории и тот же порог, что и
  у остальных типов.
- Отсутствие адресата, отправителя, основания правоотношения, требования или
  расчёта при денежном требовании — блокирующая ошибка.

### M6 — document-quality-gates

**Что:** единый набор аудитов, применяемый ко всем четырём типам перед DOCX.

**Acceptance criteria** — до сборки DOCX выполняются:

| аудит | реализация |
|---|---|
| factual consistency | сверка сумм/дат/сторон документа с материалами |
| party/role consistency | истец≠ответчик, роль соответствует типу документа |
| timeline consistency | даты не противоречат друг другу |
| contract consistency | реквизиты договора совпадают с материалами |
| calculation audit | M3 |
| legal citation audit | `citation_audit.py` |
| applicability audit | `legal_basis_fit.py` |
| temporal validity audit | редакция нормы на релевантную дату |
| procedural audit | подсудность, досудебный порядок, госпошлина |
| evidence audit | каждое доказательство есть в материалах |
| prayer consistency | просительная часть следует из фактов и расчёта |
| language/style audit | нет мета-фраз AI |
| internal-reasoning leakage audit | нет `NEEDS_VERIFICATION`, `KORGAN`, `reasoning` в теле |
| DOCX renderer audit | `rendered_docx_blockers` |

- Существенная ошибка блокирует релиз или переводит документ в
  `preliminary` (controlled verification path). Молчаливый выпуск невозможен.
- В иске истца не может быть раздела прогнозируемых возражений ответчика.

### M7 — regression-and-evaluation

**Acceptance criteria**

Позитивные сценарии (каждый — отдельный тест):
подряд · услуги · поставка · аренда · долг/заём · договорная неустойка ·
частичная оплата · несколько требований · досудебная претензия ·
ответ на претензию · отзыв на иск · неполные реквизиты · неправильная статья ·
устаревшая статья · существующая, но неприменимая статья · отсутствие
доказательства.

Негативные тесты ловят:
hallucinated law · hallucinated fact · hallucinated amount · wrong party ·
wrong procedural role · invalid calculation · outdated citation ·
non-applicable citation · leaked reasoning ·
defendant-objection section inside plaintiff claim.

Плюс: полный `pytest` из корня репозитория зелёный (не только по файлам).

## 7. Code style

- Python 3.11, `from __future__ import annotations`, dataclasses со `slots=True`.
- Комментарии на русском там, где объясняется юридическое требование; на
  английском — где объясняется механика кода. Совпадает с текущим репозиторием.
- Комментарий объясняет **почему**, а не **что**.
- Никаких новых монки-патчей. Существующие либо делегируют канонической
  реализации, либо удаляются с покрытием регрессией.
- Детерминированные вычисления — только `Decimal`, никогда `float`.

## 8. Testing strategy

- TDD: для каждого найденного бага — reproduce → failing regression test →
  root cause → minimal fix → green test.
- Тесты денежных вычислений выполняются **в двух режимах**: без production
  монки-патчей и после `import korgan.strict_bot`. Это структурное требование:
  именно его отсутствие скрыло BUG-1/2/3.
- Никаких сетевых вызовов и вызовов OpenAI в тестах.
- Полный `pytest` из корня обязан быть зелёным.

## 9. Boundaries

**Always**

- Ветка работы — от `recovery/miniapp-api-1600-sg`, PR туда же.
- Каждая правка — маленький логический коммит.
- Перед каждым коммитом — прогон затронутых тестов.

**Ask first**

- Изменение схемы БД.
- Изменение публичного контракта MiniApp API (поля ответов).
- Удаление модуля целиком.

**Never**

- Работать в `main`, мержить в `main`, force-push.
- Ломать: оплату Kaspi/OFD, идемпотентность, «Мои дела», аутентификацию,
  PostgreSQL, загрузку PDF/DOCX/JPG/PNG, существующие гарантии безопасности.
- Требовать повторной оплаты после подтверждённой оплаты.
- Выдумывать статьи, пункты, названия НПА, нормативные постановления,
  судебную практику, сроки, размеры госпошлины, правила подсудности,
  номера дел, цитаты.
- Выдумывать ФИО, БИН/ИИН, адрес, номер договора, дату, сумму,
  доказательство, факт оплаты, факт направления претензии.
- Выпускать неподтверждённую точную ссылку клиенту без пометки.
- Писать `PRODUCTION READY` до выполнения всех пунктов Definition of Done.
